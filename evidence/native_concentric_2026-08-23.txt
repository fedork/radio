Native C implementation of concentric round expansion, radio_oracle.c, 2026-08-23
Status: measured. New command: `concentric <k> <n1> <m1> ...`, additive only -- radiobase.c is
untouched, exactly the same discipline as the existing `enumerate` command. Every leaf check calls
the existing, trusted `canSolveB` unmodified; only the split-ordering/round bookkeeping is new.

SCOPE NOTE, stated up front because this work was done overnight without the user present: this
prototypes and validates the design at real scale (k7 and k8 census endpoints). It does NOT touch
data/pareto_sb.csv, does NOT modify radiobase.c's trusted solving logic, and does NOT claim any new
mathematical fact -- every "winner" reported below either matches an already-certified census
literal winner exactly, or is independently verified via the same canSolveB call the rest of this
codebase already trusts, on a state whose census entry already records it as solvable via other
winners. The literal cold Sa(193) run (the canonical ~4.85-CPU-day benchmark) was deliberately NOT
attempted -- that is a real, expensive, high-stakes production run this repo's own conventions say
needs a check-in first, not something to launch unsupervised overnight.

=====================================================================================
1. WHY GO NATIVE: THE PYTHON PROTOTYPE'S OWN CEILING
=====================================================================================
tools/ml/proto_concentric_rounds.py (evidence/concentric_round_search_2026-08-22.txt) validated
the design at n=10 real k7 endpoints via the persistent AWS oracle over TCP -- 100% success,
oracle calls in the hundreds to low thousands. But every check paid a network round trip plus
Python overhead (~50-100ms/call observed all session), which caps what is testable: a few thousand
calls per endpoint was already 60-480s wall-clock. k8 endpoints have stage-2 pools in the millions
(evidence/deficit_order_and_bestfirst_2026-08-22.txt section 4); testing there over the same
channel was never going to be practical. Porting the mechanism natively -- same design, calling
canSolveB in-process instead of over a TCP+Python client -- removes that ceiling entirely.

=====================================================================================
2. A REAL BUG FOUND WHILE PORTING: THE EARLIER "BY_MAGIC3 BENCHMARK" MEASURED THE WRONG DIRECTION
=====================================================================================
Section 6 of evidence/concentric_round_search_2026-08-22.txt benchmarked a Python port of
`magic3()`/`distance()` against the deficit signal, concluding "no clean winner." Re-reading
radiobase.c while building the native version found: `indexSpl` (radiobase.c:2737-2757) sorts by
`descSpl`, which orders DESCENDING (`b1->sort - a1->sort`, radiobase.c:2740). `HOIST_ORDER`
(radiobase.c:363-370) does not mark `BY_MAGIC3` as reversed, so it walks `ind[BY_MAGIC3]` forward
from position 0 -- i.e. the REAL solver visits the LARGEST magic3 value (least balanced) FIRST and
the smallest (most balanced, 0 at the true midpoint) LAST. tools/ml/proto_concentric_rounds.py's
`magic3_key` port sorted ascending (Python's default `sorted()`), i.e. most-balanced first -- the
OPPOSITE direction from what `radiobase.c` actually does.

This means the earlier "magic3 vs deficit, no clean winner" comparison measured an UNTESTED
direction of BY_MAGIC3, not the one deployed. That prior finding is not retracted (it may still
hold, or may not) -- it is downgraded to "inconclusive pending a same-direction re-test," and
flagged in docs/status.md accordingly. The native version reads `sp->ind[BY_MAGIC3]` directly and
walks it exactly as `HOIST_ORDER` does, so it is not exposed to this bug regardless.

=====================================================================================
3. A SECOND REAL BUG, CAUGHT BY GOING NATIVE, NOT BY REASONING ABOUT IT FIRST
=====================================================================================
The first native version treated all P segments symmetrically: a single round-shared radius grown
over every segment together (growth factor `G^(1/P)`), no segment singled out for full coverage --
reasoning that the Python design's "one segment always full, ML-scored" treatment existed only to
amortize an expensive score, and BY_MAGIC3 lookups are already free, so the distinction should not
matter. Measured immediately on the same 10 already-validated k7 endpoints: still 10/10 successes,
but the fraction of the FULL raw combinatorial space needed before finding a winner was 64-99%
(median 0.83) -- effectively no better than `enumerate`'s own unpruned walk, the exact failure mode
this whole design was meant to fix.

Diagnosis: the reasoning was wrong about WHY the asymmetric structure worked. It is not about
scoring cost -- it is that most winners in this population need exactly ONE part to sit deep in
its own per-part order while the rest stay comfortable (independently established already, by the
per-part deficit saturation finding in evidence/deficit_order_and_bestfirst_2026-08-22.txt: most
mass-feasible candidates sit at the single worst per-part value on some part). A symmetric radius
box needs ALL P segments to reach that depth simultaneously to cover such a winner; an asymmetric
design that always fully covers ONE segment only needs that ONE designated segment to happen to be
(or contain a good option near) the deep one, with the other P-1 needing only modest radius.

FIX: restored the asymmetric structure -- pick the segment with the SMALLEST admissible-option
count as "last" (cheapest full inner loop), grow radius over the other P-1 with growth factor
`G^(1/(P-1))`. Re-measured on the same 10 k7 endpoints: still 10/10, round-of-success stayed in a
similarly narrow band (16-20), but this did NOT meaningfully reduce the raw-space fraction needed
(still 64-96%, see section 4) -- see the reframing in section 5.

=====================================================================================
5. REFRAMING WHAT THE DESIGN ACTUALLY BUYS, NOW THAT IT CAN BE MEASURED PRECISELY
=====================================================================================
The Python-era framing ("round of success stays in a narrow band, so it finds winners EARLY, i.e.
checks only a small fraction of the space") is not what the numbers above show. Round-of-success
IS narrow (16-20 at k7) -- but the FRACTION of the true raw combinatorial space checked before
success is 64-96%, not small. These are different claims, and the round-based Python metric never
distinguished them because the Python version never measured against the TRUE raw_space (it
compared against R_0-survivor counts and oracle-call counts, not the product of true per-part
admissible sizes computed here).

The honest, corrected claim: concentric round expansion's real value is (a) a predictable,
narrow-banded STOPPING POINT (still true, and still more principled than an arbitrary CPU-unit
cutoff), combined with (b) native C being fast enough that even needing most of a real state's
raw space is still fast in absolute terms (a few seconds at k7, tens of seconds at k8, see section
6) -- NOT "avoids most of the search space." Whether a real *sound* early-stopping design (finding
winners after checking only a small fraction) is achievable at all is still open; this design does
not demonstrate it, even though it demonstrates something else useful (bounded, predictable,
practically-fast search).

7. A REAL SAFETY GAP FOUND AND FIXED: NO OVERALL DEADLINE ON THE SEARCH LOOP
=====================================================================================
Sampling more broadly (60 random forced 4-part k8 endpoints, not just the highest-mass 8) hit one
state with an unusually lopsided part (n:m = 33:6, 43:2 among its four parts) that ran past 4
CPU-minutes with no way to stop it short of killing the process -- `concentric_search`'s inner loop
had no deadline check at all, unlike every other search path in this codebase, which all respect
`query_budget_seconds` on individual `canSolveB` calls. A single pathological state could have
blocked an unattended batch indefinitely.

Fixed by adding an overall deadline (`query_budget_seconds * 5`, reusing the existing `budget
<seconds>` knob, checked every 2^20 combinations so it costs nothing on the fast path) that bails
out with `success=no ... reason=timeout` rather than running unbounded. Re-tested the SAME
lopsided-part endpoint standalone afterward: it actually completes on its own in 112s (round 24,
matching the pattern above) -- the earlier 4+ CPU-minute run was inside a long-lived process that
had already accumulated cache from several prior real states, and cache-lookup cost in this
codebase is independently documented as hump-shaped, non-monotonic, and NOT safe to extrapolate
(docs/status.md's existing "cache-load cost is hump-shaped" trap, now confirmed to apply to
per-query lookup cost within a long batch too, not just bulk cache loading). The fix is kept
regardless -- a single-state 112s outlier discovered by luck does not mean the true worst case is
bounded; the deadline is the actual safety net, not this one measurement.

9. THE TIMEOUT FIX FROM SECTION 7 HAD A GAP TOO -- FOUND BY WATCHING IT FAIL LIVE
=====================================================================================
Section 7's fix (deadline checked every 2^20 raw combinations) assumed roughly uniform per-check
cost. Watching the 60-endpoint batch live exposed why that assumption is wrong: the mass/cap
feasibility check is cheap, but a candidate that PASSES it triggers up to three real `canSolveB`
calls, and this codebase's own already-documented behavior is that an individual canSolveB call
can legitimately run up to its full per-call budget in real wall-clock terms (docs/status.md's
existing "queries budgeted at 5 nominal seconds took up to 270 real seconds" trap). A handful of
such slow, feasible candidates in a row can burn through several minutes before the 2^20-counter
checkpoint is ever reached again, since between two feasible candidates there can be hundreds of
thousands of cheap infeasible ones incrementing the counter quickly, but the checkpoint's timing
was calibrated for uniform-cost work, not for a mix dominated by rare expensive calls. A k8 state
with parts (26:7),(41:4),(27:5),(51:1) ran to 11+ CPU-minutes past the intended 300s bound before
being killed by hand.

FIX: check the deadline again immediately after every completed canSolveB attempt (not just on
the raw-check counter) -- these are already the rare, expensive branch, so the extra check costs
nothing on the common fast path. Re-tested the SAME triggering state standalone with a tighter
`budget 15` (75s intended overall bound): now bails out cleanly with `reason=timeout` at 123s
(some overshoot remains, bounded by roughly one more slow canSolveB call's own budget beyond the
deadline -- not the previous unbounded 11+ minutes). This is the second real, live-caught gap in
the safety net this session, not the design itself -- worth remembering as a general lesson: a
periodic-counter deadline check is only as good as its assumption about per-iteration cost being
roughly uniform, and any codebase with a documented "some individual operations are much slower
than typical" behavior needs the check anchored to those expensive operations directly, not to a
counter that assumes they don't exist.

The 60-endpoint broader sample was relaunched a second time with this fix and an explicit tighter
`budget 20` (100s overall bound per endpoint) -- see the SUMMARY appended below, or
docs/journal.md's dated entry, for the completed result.

11. THREE DESIGN CORRECTIONS FROM REVIEW, APPLIED AND TESTED SAME DAY
=====================================================================================
Review of section 10's results produced three concrete corrections, applied to radio_oracle.c and
retested before writing this section (not from reasoning alone).

CORRECTION 1 -- rounds replace the deadline, not sit alongside it. The overall wall-clock deadline
added in sections 7/9 was the wrong fix for the real problem: it let a search stop before
fully_saturated, and a capped "no" is indistinguishable, from the caller's side, from a genuinely
exhaustive one. Removed entirely (both the outer counter-based check and the post-canSolveB check),
along with the `max_rounds` cap that had the same silent-early-return property (round could exceed
40 for a large enough segment before saturating -- section 10's own results never actually hit this,
but it was a live risk, not a theoretical one). The loop now stops for exactly one of two reasons: a
confirmed winner, or true fully_saturated. Termination is still guaranteed: R[i] grows by >=1/round
and is capped at sz[outer[i]].

CORRECTION 2 -- MAYBE is fine at the intermediate level (one candidate's child check), never at the
top. A candidate whose child canSolveB call returns MAYBE (its own bounded deadline) is correctly
not counted as a confirmed winner -- but if the search reaches full saturation with no winner AND at
least one candidate along the way left a child unresolved (MAYBE, not a clean FALSE), the "no" is
NOT the same claim as canSolveB's own exhaustive negative would be. Added `has_maybe` tracking; a
saturated "no" now reports `reason=unresolved_children` when this happened, so nothing downstream
reads an inconclusive result as a proof. (Not exercised in this round of testing -- every endpoint
below found a confirmed winner -- but now structurally in place.)

CORRECTION 3 -- widened the round-1 starting radius (R0 = 8 per outer segment, was implicitly ~2)
to test the hypothesis that an easy state should converge by round 1, and if it doesn't, that's a
signal to fix ordering or widen the start.

RESULT OF CORRECTION 1, retested directly: the 5 endpoints that timed out in section 10
(U000035, U001260, U001766, U001702, U001598 -- all lopsided-part, all wins=1) now ALL succeed with
no deadline at all: round 15-16, frac 0.68-0.996, 8 CPU-minutes combined for all 5. They were never
stuck or pathologically hard -- they were victims of a deadline that was too tight relative to how
much of the raw space this design generically needs, and their outer-segment sizes (147-240) simply
made each round's cost proportionally larger. Removing the deadline was the correct fix, not a
bigger deadline.

12. THE TOP LEVEL NOW FORCES REFUTATION: RESOLVE AMBIGUOUS CANDIDATES BEFORE DECLARING "NO"
=====================================================================================
Follow-up correction to section 11's MAYBE handling, from further review: tagging a saturated "no"
with `reason=unresolved_children` was honest but incomplete -- the design goal is that the top level
"expands until either a solution is found or refutation is achieved," not that it gives up and
labels the uncertainty. The fix does not require reimplementing canSolveB_ctx's recursion: this
codebase's search budget is deterministic by default (RADIO_WORK_BUDGET, radiobase.c) -- a count of
accepted split prefixes, not wall-clock time -- and canSolveB_ctx already implements exactly the
parent-to-child budget propagation this needed ("a child consumes its parent's allowance," and
"budget exhaustion returns MAYBE rather than FALSE" per radiobase.c's own comment). So a MAYBE from
canSolveB during the sweep is already a bounded-effort, honestly-caveated answer, not a wall-clock
artifact; the only missing piece was making the top level spend MORE of that same trusted mechanism
on genuinely ambiguous candidates before giving up.

Added: every candidate whose children include a MAYBE during the sweep is now remembered (bounded
at 4096 entries; more sets an honest overflow flag rather than growing unbounded). Once the round
loop reaches full saturation with no confirmed winner, if any candidates were left ambiguous, the
top level re-verifies each one's children with NO_DEADLINE (unbounded, using canSolveB's own
existing, cached, trusted recursion, unmodified) before finalizing. Only if every remembered
candidate resolves to a genuine FALSE (and the list never overflowed) does "no" go out clean; a
resolve-pass TRUE is reported as a real winner (tagged `resolved_ambiguous=yes`); anything still
ambiguous after that (overflow, or the rare case NO_DEADLINE's own 1000-nominal-second per-level
cap still isn't enough) keeps the `reason=unresolved_children` tag rather than silently becoming a
false refutation.

VALIDATION. Natural MAYBEs proved too rare to trigger by chance: budget 1 (20,000,000 work units per
child, the tightest the `budget <seconds>` protocol command can express) never produced a single
MAYBE across all 43 real endpoints tested so far (10 k7 + 8 k8-hardest + 20 k8-diverse + 5
previously-timed-out) -- this population's child checks all resolve well within that budget in
practice, consistent with the earlier "0.000 seconds, totalsplits<100" character of the great
majority of sub-solves seen in these logs. Exercised the resolve-pass code directly instead with a
temporary, reverted-before-commit test hook (an env var forcing an arbitrarily tiny child budget,
in raw work units rather than whole seconds) on two already-validated endpoints:

  - Forcing every child check to ~1 work unit against a 21.75M-raw_space k7 endpoint: every
    candidate went MAYBE, the ambiguous list hit its 4096 cap immediately, and the search correctly
    reported `success=no ... resolved_ambiguous=4096 reason=unresolved_children` rather than a false
    clean refutation -- the overflow-honesty path works.
  - Forcing every child check to ~80,000-130,000 work units against a smaller (299,520-raw_space)
    k7 endpoint: the ambiguous list still overflowed at the lower end of that range, but the search
    still correctly located and confirmed a genuine winner (34:15,71:0,0:24,0:27 -- a different
    valid split from the one the unbounded sweep finds first, evidence this state has more than one
    literal winner) via the resolve pass, reporting `success=yes ... resolved_ambiguous=yes`; at the
    upper end (130,000, no overflow) the same winner was found cleanly. The "promote an ambiguous
    candidate to a confirmed winner" path is confirmed working, not just theorized.

Reran the full 10-endpoint k7 regression after removing the test hook: byte-for-byte identical
round/checked/frac numbers to the pre-hook build. No behavior change for the realistic default
budget (60 nominal seconds = 1.2 billion work units per child check), where MAYBE essentially never
arises in this population -- the correction matters for correctness guarantees and for any future
run at a tighter budget, not for today's default numbers.

13. RADIUS PROPAGATION REPLACES WORK-UNIT CURRENCY IN canSolveB_ctx ITSELF
=====================================================================================
Direct follow-up to "the deadline propagation was there already... now we just want to replace
that with radius propagation instead." Section 12 escalated ambiguous candidates to NO_DEADLINE
(unbounded work-unit budget) via the UNMODIFIED canSolveB -- correct, but the currency children
were bounded by during the exploratory sweep was still radiobase.c's existing deterministic
work-unit clock, not radius. This section replaces that currency inside canSolveB_ctx itself.

DESIGN, arrived at over three iterations, each corrected by a real problem the previous one hit:

Iteration 1 (rejected before writing code): treat radius as "totalsplits <= N" -- a raw count of
full joint-combination candidates tried at a level, reusing canSolveB_ctx's own totalsplits
counter directly as the currency in place of the work clock. Rejected on reflection: N compared
against a TOTAL-combinations count scales unevenly across states with different part counts (a
budget of 1000 total combinations gives a 4-part state ~5.6 options per part but a 2-part state
~31.6), which is not what "the same radius at every level" should mean.

Iteration 2 (built, found broken by testing): "radius = totalsplits, absolute propagation" as
above. Compiled and ran; the very first k7 batch hung with pass counts in the tens of millions.
Root cause: canSolveB_ctx's existing iterative-deepening retry (an unresolved exhaustive pass
doubles probe_seconds and starts over) assumes each retry gives children MORE budget via
probe_child_deadline's growing quantum -- radius mode's absolute (unchanged) child propagation
means retrying with the identical child radius can never make progress, so the loop retried
forever. Fixed: radius mode now stops after exactly one exhaustive pass instead of retrying --
confirmed safe by tracing the code, since canSolveB_ctx already returns MAYBE unconditionally
whenever skipped_some is true at loop exit (line ~2621), regardless of why cont2 became 0.

Iteration 3, the one that stuck: radius = "top-N candidates tried, per segment, at every level" --
so a 1-segment state explores N total, a 2-segment state N^2, a 4-segment state N^4, uniform
across depth and part count. Implemented by capping each level's OWN splitindex[] range at
min(its true size, N) directly, rather than comparing an aggregate counter to a threshold. This
needed real correctness engineering, not just a currency swap:

  - CORRECTNESS HAZARD, caught before it was ever run: capping a level's own candidate range below
    its true size means a pass that finds only clean FALSEs within the cap proves NOTHING about
    the candidates outside the cap. Added a new radius_truncated flag, set the moment any level's
    splitindex is actually capped below its real size, and threaded it into every path that could
    otherwise conclude a definitive FALSE (both the "!skipped_some -> cont2=0" branch and the
    post-loop "else if (skipped_some) return MAYBE" check, plus the frozen_refute early return) --
    a truncated search can only ever end in MAYBE or a genuine TRUE (a witness found inside the cap
    is unconditionally valid regardless of what was never looked at), never a manufactured FALSE.
    Verified directly with a tiny standalone harness: canSolveB_ctx with radius_mode=1 and N=1 on a
    real solvable 4-part k5 state returns MAYBE (not FALSE); the same call with N=2^40 returns TRUE.

  - A GENUINELY NEW FACT, found by tracing the exact index arithmetic, not assumed: canSolveB_ctx's
    own internal walk of BY_MAGIC3 goes the OPPOSITE direction from concentric_search's own
    top-level sweep. ORDER_REVERSED[BY_MAGIC3]=0, so HOIST_ORDER sets ordp/ords to walk forward
    from index 0 -- but the actual loop pre-decrements splitindex[i] (initialized to the level's
    full size) before every use, so the FIRST candidate tried is index size-1, counting DOWN to
    index 0 last. Combined with ind[BY_MAGIC3] being sorted DESCENDING (index 0 = largest magic3 =
    least balanced), this means canSolveB_ctx's own recursion tries MOST-balanced-first, while
    concentric_search's top level (reading ind[BY_MAGIC3][idx] for idx=0,1,2,...) tries
    LEAST-balanced-first -- confirmed by the code's own comment ("walks the descending-sorted
    index from the far end, i.e. in ascending key order"). Not a bug (MAYBE is always safe either
    direction) but a real inconsistency for "radius means the same thing at every level." Fixed,
    per explicit direction, by making radius mode reverse BY_MAGIC3 specifically inside
    HOIST_ORDER, so every level -- top and recursive alike -- walks least-balanced-first.

  - Forced splitincr[i] = BY_MAGIC3 unconditionally at every level in radius mode (overriding the
    existing size/pass-tuned BY_SP0/1/2 heuristic selection), so "radius" refers to one consistent
    order everywhere, not a different metric depending on which heuristic canSolveB_ctx would
    otherwise have picked for that specific level.

  - radio_effort_now_ctx (the totalsplits-vs-deadline comparison used everywhere in iteration 2)
    is now inert in radius mode (returns 0 unconditionally) -- correctness-and-progress bounding
    is entirely structural (the splitindex cap) now, not an auxiliary counter comparison, which
    would otherwise fire almost immediately for any part count > 1 since N is a per-segment count.

IMPLEMENTATION SCOPE. All in canSolveB_ctx and its budget helpers (search_deadline,
probe_child_deadline, HOIST_ORDER, radio_effort_now_ctx) in radiobase.c, gated entirely behind a
new radius_mode field on radio_search_context, default 0 (off) for every existing context and
caller. radio_oracle.c creates one dedicated radius_ctx (radius_mode=1) for concentric_search's
own child verification, separate from radio_default_search_context used by canSolveB/enumerate/
cache loading -- both still share the same global dominance trie, so a fact either proves is
immediately available to the other. Never passes NO_DEADLINE through radius_ctx (radius mode would
misread the sentinel value 2 as a radius cap of 2); RADIUS_UNBOUNDED (2^40) plays that role instead
for the resolve-ambiguous-candidates pass from section 12.

VALIDATION. Reran every endpoint tested so far under this design: all 43 (10 k7, 8 k8-hardest, 20
k8 mass/wins-diverse, 5 previously-hardest) succeed, and every substantive field -- round, checked,
raw_space, frac, and the literal WINNER split reported -- is BYTE-FOR-BYTE IDENTICAL to the
extensively-validated work-unit-currency results from sections 10-12 (only the provenance banner's
build_id/commit/timestamp differ). Given section 10 already confirmed 55/55 of that design's
winners exactly match independently-certified census facts, this transitively carries the same
correctness weight to the radius-currency design: it isn't just internally consistent, it
reproduces the identical, externally-verified answers.

Confirmed no regression to the default (radius_mode=0) path throughout: plain VERDICT queries and
the `enumerate` command (both still using radio_default_search_context) produce byte-identical
output to the pre-this-section binary at every stage of this rewrite.

=====================================================================================
14. SIMPLIFIED: DROP AMBIGUOUS-CANDIDATE STORAGE, RE-SWEEP INSTEAD
=====================================================================================
Follow-up correction, per direct feedback: section 13's has_maybe resolution stored up to 4096
ambiguous candidates in fixed arrays (ambig_sb0/sb2/sb1) to re-verify individually with
RADIUS_UNBOUNDED. Unnecessary complexity, and it carried a real overflow risk (ambig_overflow) if
more than 4096 candidates were ever left ambiguous in one sweep. Simpler and equally correct: drop
the storage entirely, and when has_maybe is set at full saturation, re-sweep the ENTIRE candidate
space once more (every outer x last combination, not just "new" ones) with RADIUS_UNBOUNDED for
every child check. No candidate-remembering needed: the shared dominance trie already holds every
fact this run has proven, so an already-resolved (TRUE/FALSE) candidate is an instant cache hit on
the re-sweep, and only the genuinely still-ambiguous ones cost real recursive work a second time.

Validated directly with a temporary (reverted before commit) test hook forcing round_radius to a
constant instead of the real R0*g^(round-1) schedule:
  - round_radius=2: identical results to the unforced run on all 10 k7 endpoints -- N=2 per segment
    already sufficed for every child check this population needed, no re-sweep ever triggered. This
    itself is informative: many recursive sub-calls bottom out via the theorem-based base cases
    (singleton/star-expansion majorization, the pairs-vs-power3[k] counting bound) that don't
    consult radius at all, so real truncation is rarer in practice than the raw N might suggest.
  - round_radius=0 (guarantees radius_truncated on every nontrivial call, forcing has_maybe): the
    sweep correctly exhausted to frac=1.0000, triggered exactly one re-sweep (confirmed via the
    stderr log), and the re-sweep correctly found the SAME previously-validated winner via
    RADIUS_UNBOUNDED -- with no meaningful slowdown (comparable total wall time to the unforced
    run), confirming the cache-hit argument empirically, not just in theory.

Reran the full 43-endpoint battery (10 k7, 8 k8-hardest, 20 k8 diverse, 5 previously-hardest) after
this simplification: every result remains byte-for-byte identical to sections 10-13's numbers, and
the default (radius_mode=0) path -- plain VERDICT queries and enumerate -- is unaffected.

=====================================================================================
15. NO_DEADLINE NOW MEANS "PROGRESSIVELY WIDEN, RECURSIVELY" -- AND A DIRECT TEST OF
    WHETHER concentric_search IS STILL NEEDED
=====================================================================================
Two follow-up corrections, per direct feedback, plus the resulting direct test of a genuinely
different architectural question: does concentric_search's bespoke top-level sweep still earn its
keep once canSolveB_ctx itself can progressively widen?

CORRECTION A -- kept the pre-existing per-level heuristic (BY_SP0/1/2/DESC, size<=3 special-cased,
the counting-bound-driven `chosen` selection) instead of forcing BY_MAGIC3 everywhere in radius
mode. That override (section 13) was a reasonable first cut to fix the direction-mismatch finding,
but it discarded prior art: this heuristic is already segment-count/index-conditioned and has its
own measured wins ("3.5x fewer candidate evaluations," 2026-08-08). Reverted; HOIST_ORDER's
radius-mode BY_MAGIC3 reversal is removed too (moot once BY_MAGIC3 isn't forced). Regression: byte-
identical to sections 13-14 on all 43 endpoints -- this population's canSolveB_ctx calls apparently
don't need the ordering forced to matter, at least not yet; ordering remains open for iteration.

CORRECTION B -- real progressive widening for radius currency, replacing the earlier "stop after
one exhaustive pass" fix (section 13) for the specific case that was asked for: a call made with
NO_DEADLINE. Added `radius_grows` (true iff radius_mode and parent_deadline==NO_DEADLINE) and
`radius_N`, a per-call cap that starts small (4) and DOUBLES on every unresolved exhaustive pass
when radius_grows -- real widening, mirroring the work-budget clock's own probe_seconds-doubling,
rather than a repeated identical attempt. Bounded (non-growing) radius calls still take exactly one
pass, as before -- MAYBE remains an acceptable answer at that intermediate level. Children of a
growing call get NO_DEADLINE themselves (not a finite slice), so widening propagates recursively,
all the way down, exactly as asked.

A real corruption bug surfaced and was fixed while wiring this up: the pre-existing work-budget
"double this root's absolute allowance" logic and probe_child_deadline both read `deadline`
directly, which stays the literal NO_DEADLINE sentinel (2) for the whole call in radius mode (by
design, so `no_deadline`/`parent_deadline==NO_DEADLINE` checks keep working). The work-budget
doubling line computed `deadline - budget_start` where budget_start is a work-clock value unrelated
to radius currency -- an unsigned underflow that radio_budget_add's own overflow clamp turned into
UINT64_MAX, which would then have been handed to a child as `cd`, indistinguishable from a plain
huge finite cap rather than the sentinel meaning "you also widen." Fixed by gating that doubling
logic to work-budget mode only, and computing the child's cd explicitly in radius mode
(NO_DEADLINE if radius_grows, the unchanged fixed cap otherwise) rather than routing through
probe_child_deadline, which has no way to see radius_grows.

THE DIRECT TEST. With both corrections in place, does a PLAIN canSolveB_ctx(&radius_ctx, sb, size,
k, NO_DEADLINE) call -- with NO concentric_search wrapper, no asymmetric last-segment structure,
just canSolveB_ctx's own existing per-level heuristic and the new recursive progressive-widening --
correctly and efficiently answer the same top-level 4-part queries concentric_search was built to
answer? Ran all 10 k7 + 8 k8-hardest + 5 previously-hardest + 20 k8-diverse endpoints (43 total)
this way, bypassing concentric_search entirely:

  - 43/43 correctly return TRUE (matching every known-solvable census fact tested throughout this
    thread) -- full correctness held.
  - The 10 k7 and 8 k8-hardest endpoints resolve in 0.00-0.27s EACH -- roughly two to three orders
    of magnitude faster than concentric_search's own reported times for the identical endpoints
    (concentric_search: ~3.7s/endpoint average for k7, ~7s/endpoint average for k8-hardest). The
    20 k8-diverse endpoints mostly resolve in well under a second, a few taking several seconds.
  - BUT: the 2 most lopsided-part endpoints from the "5 previously-hardest" set (the ones with
    41:4/51:1 and 46:2/50:1 parts, the SAME shape that triggered both deadline bugs earlier today)
    took 494s and 300s respectively -- SLOWER than concentric_search's own handling of those same 5
    endpoints (8 CPU-minutes combined, ~96s average). No timeout, no MAYBE, no false answer -- they
    correctly resolved to TRUE, just slowly.

CONCLUSION, stated honestly rather than as a clean verdict either way: baking progressive radius
widening into canSolveB_ctx itself, using its existing heuristic, is a dramatic win for the
overwhelming majority of states tested -- and eliminates the need for concentric_search's bespoke
sweep code for those. But it is not a strict improvement: the specific lopsided-part failure mode
this thread already identified twice today is WORSE under this design than under
concentric_search's own asymmetric "last segment always full" structure, not just comparably slow.
Whatever concentric_search's design was doing specifically for that shape (forcing full coverage of
one narrow segment immediately, rather than growing all segments' radius together) appears to be
solving a real problem the existing per-level heuristic does not. This is now a genuine, evidence-
backed design fork rather than an obvious simplification, and is left open rather than resolved
unilaterally: whether to retire concentric_search, keep it as a fallback for lopsided-part shapes,
or investigate why canSolveB_ctx's own heuristic struggles specifically with those.
