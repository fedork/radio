## Design and soundness

The durable fact array remains in its canonical `(part count,largest n,total mass,fact)` order.
That preserves exact hashing and readable certificate order. The verifier now builds a separate
immutable permutation in `(part count,largest segment product,total mass)` order and scans
structure-of-arrays columns in that order:

    int32 canonical fact index
    int32 total mass
    8 x uint8 sorted n profile
    8 x uint8 sorted m profile
    4 x uint16 sorted segment-product profile
    int32 end of equal-largest-product group

If a fact injects componentwise into a query, every mapped segment has no larger `n`, no larger
`m`, and no larger product. Sorting each scalar multiset therefore gives three independent
necessary componentwise inequalities. The product profile is complete for the run9 k=6 index,
whose facts have at most four segments; it remains a sound but weaker top-four test for longer
states. The existing exact bipartite injection matcher is still the final decision. No implied
fact is inserted, no certificate claim is added, and no approximate rejection is accepted.

This is bounded denormalization, not closure materialization. Relative to the legacy index it adds
20 bytes per fact (8 product-profile + 4 order + 4 mass + 4 group-end), about 62.5 MB over the
3,126,190-record normalized run9 input before allocator effects. `VERIFY_LEGACY_INDEX` restores the
old `(part count,largest n,total mass)` index for an exact control, and `VERIFY_INDEX_STATS` adds
candidate counters. Neither flag changes certificate semantics.

Both builds used the exact source SHA-256
`c54631980dd817e02bca2ed7d0eff7b3694276c17a03dee02554aa45299cf5a3`:

    tools/build_radio.py -O3 -pthread -Wall -Wextra -Wpedantic \
      radio_verify.c -o /tmp/radio_verify-final
    build ID 144123aba3cffed2cdd4c81c6457c187801148e0de93d3bfcc23b7626cc73188

    tools/build_radio.py -O3 -pthread -Wall -Wextra -Wpedantic \
      -DVERIFY_LEGACY_INDEX radio_verify.c -o /tmp/radio_verify-final-legacy
    build ID e645a42e59e6880e6c6a31c5390de495a558882185f7f283ac24765de57c5a98

The final positional `2` is the input-source mask: it excludes facts from the first input as
targets while leaving them available as the support database. Explicit `ROOTS` are additive; they
do not otherwise suppress ordinary targets.

    ROOTS=/tmp/product-root-378086.cert VERIFY_THREADS=1 VERIFY_MEMO_BITS=20 \
      tools/capped_run.sh --seconds 600 --rss-gb 8 --label LABEL -- \
      tools/run_with_provenance.py BINARY /tmp/run9-cache-study.cert \
        7 0 1 3 0 999 1 0 1 0 2

    k=2 5; k=3 424; k=4 137,457; k=5 9,341; k=6 65,371; k=7 431

Coloring the nine explicit roots verified every target and emitted a canonical-order certificate:

    roots          9
    support facts  120,293

Its fact set is byte-for-byte equal after sorting to the earlier product-reordered prototype
certificate; only root/fact presentation order differs. The production build then
replayed the canonical-order certificate through `tools/run_with_provenance.py` under the RSS/wall
supervisor:

    TOTAL verified 120302, unverified 0, budget 0,
          nodes 2491283058, 140.28 s wall on 8 threads
    external wall 141 s; peak RSS 0.88 GB

The replay log passed `tools/check_provenance.py`. Per level, it verified 5/424/49,675/9,311/
60,447/431/9 records at k=2..8 respectively. This exercises the canonical-index witness mapping,
parallel verification and the complete colored DAG, not merely the hard one-root slice.

Finally, a provenance-wrapped `CERT_ONLY` pass over run9 took five external seconds and reproduced
the normalized certificate byte-for-byte at SHA-256
`3ad5877a2ffa3bcf04c3403a147ae075e406b4313cce83eb0761fdd563725116`.

## Checks and discarded diagnostics

`tools/test_radio_verify.sh` passes serial/parallel verification, coloring, minimalization and text
replay. The final default build also passes AddressSanitizer + UndefinedBehaviorSanitizer (build ID
`63df2dde105c1d7eae441ba29d99fa4c47463e4b725e83c6e6c4e881c852f130`) and ThreadSanitizer with two
workers (build ID `0ab7bb13f2128dc079272f9358f7cb0c1ba9abf300a109b108b1a6784b8a5f3a`).

Two early sparse-sample comparisons each reached their 300-second external cap and were abandoned:
one selected fact can dominate such a sparse batch, so the exact hard-root control above is the
reproducible comparison. A later command accidentally added the explicit root without excluding
ordinary input facts and was terminated after about 6m20s of CPU; it produced no result. The source
mask in the recorded command prevents that error. No solver process or solver source was changed.
