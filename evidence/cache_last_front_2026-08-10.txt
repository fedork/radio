# Last-segment Pareto-cache implementation measurements, 2026-08-10

Scope
-----

Candidate: origin/main 23de2ac plus the compact cache implementation subsequently committed.
Machine: Apple M4 Pro, 24 GB, macOS; all runs single-threaded.
Checkpoint source: sa193-local-2026-08-10:out_sa193.txt, filtered by k without reordering.
The three replay files contain 107,981 k=5, 98,124 k=6, and 6,466 k=7 lines.

The implementation keeps exact prefix traversal but folds the final part into maximal-positive and
minimal-negative 2-D Pareto fronts.  Every child entry is a tagged uint32 descriptor.  Singleton
fronts are inline; non-singletons use small vectors; retained branches use uint32 child arrays.

The pre-change dense pointer trie reserves 5,585,395,760 bytes for the same k=5..7 replay; its
per-level counts are independently retained in cache_shape_sa193_local.txt.  Thus the implemented
cache reduces requested result-cache storage 11.174x, or 91.05%.  Requested storage excludes malloc
metadata and fixed solver tables; maximum RSS includes them, so those two figures are not mixed.

Verdict regression against the old trie
---------------------------------------

tools/cache_query_regression.c first verifies every exact checkpoint fact, then emits one byte per
targeted easier/harder/prefix/extension mutation and 500,000 deterministic valid random states.
The source was compiled once against the pre-change engine and once against the candidate.  Full
byte comparisons (not hashes) gave:

  k=5: 1,811,621 queries; 3,642 old MAYBE -> new TRUE; no other difference
  k=6: 1,773,102 queries;   935 old MAYBE -> new TRUE; no other difference
  k=7:   580,235 queries;    45 old MAYBE -> new TRUE; no other difference
  total: 4,164,958 queries; 4,622 old MAYBE -> new TRUE; no lost or reversed verdict

The strengthening is expected and sound: an exact positive child folded into a last-part front also
answers componentwise-smaller last parts that the old canonical closure did not always materialise.
Negative answers were required to match exactly.  An early prototype that returned from an entire
negative recursive call lost two old negative mutation hits and was rejected.  The final version
skips only dominated child edges while continuing all other segment permutations.

Other correctness gates:

  * all 1,039 CHECK lines from tools/split_regression.c match the old engine;
  * that corpus and a 10,000-fact replay pass ASan+UBSan;
  * radio_print renders 24 nodes under ASan+UBSan and check_witness.py verifies the tree;
  * main drivers, pairtab, tripletab, quadtab, and fast_replay compile against the new API;
  * MAX_N=258, 336, and 1030 variants pass syntax compilation (large ids use the uint32 fallback).

Matched hard warm-cache control
-------------------------------

Command for both engines:

  tools/capped_run.sh --seconds 180 --rss-gb 8 -- \
    radio_one warm_k5.txt 6 29 6 19 9 13 12 36 3

Both found the same split [8:1,8:4,11:11,19:2] after totalsplits=37,899.

  current: solve CPU 32.8 s; wall 55 s; peak RSS 2.40 GB
  compact: solve CPU 42.3 s; wall 65 s; peak RSS 0.78 GB

The compact measurement preceded one small checkCache de-duplication, so it is a conservative timing
for the final code.  It establishes the tradeoff but is not used as the final throughput number.

Full Sa(192) positive control
-----------------------------

Candidate command:

  clang -O3 -DMAX_K=10 -DMAX_N=193 radio_sa192_front_control.c -o control
  tools/capped_run.sh --seconds 1200 --rss-gb 12 --label sa192-front-control -- ./control

Result:

  can solve Sa(192) in 10 with following: Sa(112), Sa(80), Sb(112:80)
  CONTROL Sa(192) in 10 = SOLVABLE (819.9 CPU s)
  wall=829 s
  peak RSS=0.41 GB
  printed substate lines=167,331

The unchanged pre-change engine's same-machine control on this workload was 734.5 CPU s, retained in
docs/journal.md under the 2026-08-10 local Sa(193) trial.  The compact cache therefore costs 11.63%
CPU on the decisive long-state control.  It stayed at 98-100% CPU throughout; no swap-driven decay
was observed.  The 17 MB raw candidate log was not archived because Sa(192) solvability already has
canonical witness proofs and this run adds performance evidence, not a new mathematical fact.  Its
local SHA-256 was 0d5a9fea49d90e556a36a5c7116393f31aeb1a98cfaac192eaa4435756048579.
