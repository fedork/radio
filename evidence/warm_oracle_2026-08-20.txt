The warm-cache oracle: sizing, throughput and priming cost, 2026-08-20
Status: measured, on an Apple M-series Mac.  Driver `radio_oracle.c`, launcher
`run_radio_oracle.sh`, client `tools/oracle_client.py`, documented in `docs/tools.md`.

WHY.  `radio_one` answers one question per process, and the cost is not the solve.  `init()` runs
before the argument check and its static tables scale with MAX_N; cache replay costs more again.
Anything wanting thousands of verdicts has to amortise both.  The oracle pays them once and then
serves queries from stdin, keeping every fact it learns.

=====================================================================================
1. SIZING — measured, MAX_K=9
=====================================================================================
  MAX_N=300   init 37 s    peak RSS 0.64 GB
  MAX_N=485   init 146 s   (RSS not captured)
  MAX_N=400, MAX_K=6       205 s        (earlier measurement, radio_one)
  MAX_N=120, MAX_K=5       0.2 s        (earlier measurement, radio_one)

MAX_N only has to cover the *queries*.  The loader now skips facts it cannot represent and reports
the count, so a narrow build stays usable against a wide cache -- `parse_file` neither bounds-checks
width nor tolerates a malformed line, which is why the oracle parses its own input.  The archived
census caches reach a side-sum of 258 and Sa(193) states reach 193, so **MAX_K=9, MAX_N=300** is the
default: it covers both and inits in 37 s.

**Do not read these as a scaling law.**  The MAX_N=400/MAX_K=6 point at 205 s sits *above* the
MAX_N=485/MAX_K=9 point at 146 s.  Init and query cost both depend on the work actually required --
which states, which cache, how much refutation -- far more than on the table dimensions.  Measure a
candidate sizing; do not extrapolate one.

=====================================================================================
2. THROUGHPUT — the point of the exercise
=====================================================================================
2,200 four-part k=5 states (the matched-sampling set from
[value_level_transfer_2026-08-20.txt](value_level_transfer_2026-08-20.txt)), MAX_K=9 MAX_N=300,
started cold with no primer cache:

  wall clock, whole run                37,332 ms
  of which init                        ~37,000 ms
  of which the 2,200 queries              243 ms      => 0.11 ms per query
  verdicts                             1,120 solvable / 1,080 unsolvable / 0 maybe

Against one-shot `radio_one` at the same sizing that batch would be 2,200 x 37 s = about 22 hours;
against the deliberately undersized MAX_N=120 build used earlier, 2,200 x 0.2 s = 440 s.  Per
query the warm oracle is **~1,800x** faster than the cheapest one-shot build and ~340,000x faster
than a correctly sized one.

CORRECTNESS CROSS-CHECK.  The 1,120 / 1,080 split is *identical* to the verdicts obtained earlier by
running `radio_one` once per state over the same 2,200 inputs.  Two independent drivers, same
answers on every state.

=====================================================================================
3. PRIMING IS THE EXPENSIVE PART, AND IS USUALLY NOT WORTH IT
=====================================================================================
The archived caches are text logs replayed through `parse_file`:

  exact.cache       515,080,944 bytes   11,661,763 facts
  dominance.cache   419,264,669 bytes   10,204,438 facts

PRIMING THE FULL CORPUS: MEASURED ON EC2, AND IT IS FINE.  Everything I previously wrote in this
section extrapolated from local prefixes and was wrong.  Run `oracle-prime/20260820T165448Z`,
on-demand r7iz.xlarge (4 vCPU, 32 GiB), commit cdffe46, loaded the whole corpus:

  facts                 21,866,180   (both caches, sorted, in 88 chunks of 250k)
  setup                        110 s  (fetch + build + sort + chunk)
  load                       5,684 s  = 1.58 h,  3,847 facts/s overall
  redundant inserts     14,084,167   (64.4%)
  exit status                    0
  peak host use          ~2 GiB of 32 -- memory was never close to a constraint

The rate curve is a HUMP, not a slide, which is why every extrapolation failed:

  c0000    44,484/s        cheap positives, sorted first
  c0004..9   431-779/s     the expensive band: 36% of total time in five chunks
  c0032    70,134/s
  c0072   198,604/s        almost everything now subsumed
  c0087 1,067,487/s

My local prefix measurements (78,752/s at 50k, 61,689/s at 200k, 687/s at 800k) sampled the rise and
the collapse and missed the recovery entirely, so a "27x further along a worsening curve" reading
gave 13-plus hours against an actual 1.58.  Three points fitted to the wrong side of a hump.

SNAPSHOT, AND WHY IT IS THE POINT.  The same run dumped a snapshot at the end:

  structure     34,600,337 branches / 120,043,426 records / 26,353,897 vectors
  dump          6,672,100,991 bytes in 43 s;  667 MiB compressed
  restore       32.8 s, 2.41 GB resident -- 173x faster than replaying the facts
  correctness   2,200 independently pre-labelled k=5 states re-queried after restore returned
                1,120 solvable / 1,080 unsolvable, matching exactly; then 0.10 ms per query

Resident memory is far below the 6.67 GB file because branch slot arrays are sparse: `calloc` leaves
untouched zero pages unmapped, so most of the file never becomes resident.

COMPATIBILITY, a defect found by using the artifact.  The first version keyed a snapshot on the
build id, which includes the compiler.  The Linux-built snapshot was therefore refused on this Mac
for no semantic reason.  Compatibility is now keyed on what actually fixes the layout -- the source
commit plus MAX_K, MAX_N, MAX_SBB and sizeof(front_point).  A geometry mismatch is refused outright;
a foreign identity with matching geometry needs the explicit `restore-any` opt-in and warns.

By level, the exact cache is almost entirely k=4..6:

  k=1 2 | k=2 22 | k=3 1,826 | k=4 891,219 | k=5 8,152,992 | k=6 2,607,761 | k=7 7,686 | k=8 255

RECOMMENDATION.  Prime once on a cheap box, snapshot, and restore thereafter: 1.58 h paid once
against 33 s per start.  Start cold only for throwaway work -- 2,200 queries took 243 ms with no
primer at all, so a primer is not needed to be useful, just to be complete.

Better than priming from the archive: **journal what you compute**.  `--journal FILE` appends every
verdict in the same format the loader reads, so a session's work primes the next one. It is exactly
the states you actually ask about, and it is small.  A MAYBE is never journalled, because it is not
a fact.

=====================================================================================
4. BINARY SNAPSHOT — an alternative to replaying facts
=====================================================================================
`snapshot <path>` serializes the cache structure; `restore <path>` or `--restore=<path>` reloads it
linearly, which is O(structure) rather than O(facts x closure).

Getting it right means walking four descriptor forms: a branch (slots 0 and 1 are *front*
descriptors, 2.. are child nodes), a front record (two front descriptors), an inline node (two
packed sbb values), and inside a front descriptor either a vector handle or an inline value.
Handles are made canonical by discovery order -- a fresh process allocates 1,2,3,... so writing in
visit order and remapping every descriptor reproduces identical handles.  The header carries the
build id and MAX_K/MAX_N/MAX_SBB/sizeof(front_point); a mismatch is **refused**, because the sbb
numbering depends on MAX_N and a cross-build restore would be silently wrong.

ROUND TRIP, the test that matters.  Loading 16,099 facts built 225,146 branches, 404,821 records
and 466,552 vectors.  Dump 247 ms / 43,616,050 bytes; restore into a fresh process 212 ms; **300
queries returned identical verdicts either way**.

CAUTION ON SIZE, not yet resolved.  43.6 MB of structure for 16,099 facts is 2.7 KB per fact.  If
that ratio held to the full 21.9M corpus the snapshot would be tens of GB.  It will not hold --
closures overlap more and more as facts accumulate -- but by how much is unmeasured, and it is the
first thing the full run should report.

=====================================================================================
5. PROTOCOL NOTES THAT MATTER
=====================================================================================
* **Stream separation.**  `radiobase.c` and `canSolveB` print to stdout, which would corrupt a line
  protocol.  The oracle duplicates the original stdout for responses and repoints the C library's
  stdout at stderr *after* the provenance banner, so retained response output still passes
  `tools/check_provenance.py` while all later chatter goes to stderr.
* **MAYBE is not a refutation.**  The per-query budget defaults to 60 because an unbounded query
  would hang the daemon.  `budget 0` removes the deadline.  Recording a MAYBE as a negative is how
  the 2023 corpus acquired 37 false ones.
* **It grows forever.**  The result cache is never freed -- deliberate, but wrap an unattended
  session in `tools/capped_run.sh`.
* Requests are rejected, not truncated, when `k > MAX_K` or the side-sum exceeds MAX_N.
