## Design and soundness

The existing immutable product index remains sorted by `(part count,largest product,total mass)`.
Within each equal `(part count,largest product)` group, full blocks of 256 consecutive facts receive:

    componentwise minima of (total mass, four sorted product lanes)
    the Pareto-minimal set under those same five necessary coordinates

Mass overflow is checked before a block probe. A component-minimum failure rejects the block
immediately. Otherwise the verifier scans the Pareto front. If any fact in the block could pass the
mass/product necessary test, descending through dominated profile points terminates at a stored
minimal point that also passes. Therefore absence of a fitting front point proves that no fact in
the block can dominate the query. A fitting point proves nothing: the verifier falls back to the
unchanged per-fact product, n-side, m-side and exact injection checks.

Only full blocks inside one primary-key group are summarized, so a candidate-range endpoint never
cuts a skipped block. The same sound rejection filter is used by pre-color same-level
minimalization. No implied fact is materialized and certificate output remains canonical text.

The summaries are adaptive. Levels below 65,536 facts use the product-only loop with the dispatch
outside the hot candidate scan. This avoids paying block-front costs on the 9,311-fact level that
dominates the Sa(113) k=6 replay. The production defaults are block size 256 and cutoff 65,536;
explicit `VERIFY_PRODUCT_PROFILE` plus `VERIFY_PRODUCT_SORT` builds the exact product-only control,
while `VERIFY_NO_BLOCK_PARETO` suppresses blocks on an otherwise default build.

## Rejected first layout and tuning

The first prototype aligned blocks only by part count and tested them before the existing
over-mass group skip. It preserved the verdict and proof counts but regressed the hard query to
45.94 verifier seconds, versus 33.24 for the then-current product index. Instrumentation explained
the failure: 1,762,914,075 block probes performed 101,332,817,879 front-point tests, much of it on
positions the mass-group skip would never have visited. That layout was removed.

Aligning blocks inside equal-largest-product groups and doing the mass skip first produced the
following one-worker size sweep. All rows verified the same target with exactly 4,644,469 nodes,
5,583,390 memo hits and 5,187,272 misses. These are tuning runs across successive but logically
equivalent prototype sources, so their fine differences are not cross-build speedup claims.

    block size   verifier wall s
            32             14.88
            64             13.48
           128             12.89
           192             13.01
           256             12.74
           384             13.57
           512             13.68

An ungated size-256 prototype also replayed all 120,302 records of the Sa(113) colored certificate
with the expected 2,491,283,058 nodes, but took 143.41 verifier / 146 external seconds at 0.89 GB,
slightly worse than the 140.28 / 141-second product-only control. It built only 377 blocks and
21,080 front points. This negative result motivated the level-size cutoff rather than applying a
run9-specific win globally. An intermediate cutoff build still tested a null block pointer inside
the candidate loop and took 155.46 seconds in one noisy full parallel replay; that placement was
removed. The final dispatch chooses the plain or block loop once per dominance query.

## Small-level guard and correctness

With eight workers, the clean product-only and adaptive builds verified the same every-tenth k=6
Sa(113) sample: 6,045/6,045 targets, zero unresolved, exactly 251,437,448 nodes and 0.84 GB peak RSS.
The product-only build took 15.95 seconds and the adaptive build 15.88 seconds; the latter built no
summaries because every relevant level is below the cutoff. This is a no-regression guard, not an
estimate of complete Sa(113) wall time. Both logs and every hard-root log above pass
`tools/check_provenance.py`.

`tools/test_radio_verify.sh` now compiles a forced two-fact-block build. Its synthetic same-key
level builds two blocks and returns the same two-of-four minimal antichain as the plain index. The
ordinary serial/parallel verification, byte-identical coloring and replay checks also pass.
